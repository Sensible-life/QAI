# QAI 사업계획서 초안

작성일: 2026-03-22

## 1. 문제 인식

### 1-1. 창업 아이템의 국내외 시장 현황 및 문제점

#### 1) 소규모 개발 조직의 구조적 QA 공백

국내외 초기 스타트업과 1인 개발자, 소규모 SaaS 팀은 서비스 출시 속도를 높이기 위해 개발과 배포를 빠르게 반복하고 있다. 그러나 QA는 여전히 사람의 시간과 경험에 크게 의존하고 있어, 실제 현장에서는 QA가 필수 과정임을 알면서도 충분히 수행하지 못하는 경우가 많다.

- 1인 개발자 또는 소규모 팀은 QA 전담 인력을 두기 어렵다.
- 개발 일정이 촉박할수록 QA 시간은 가장 먼저 축소된다.
- 비전공자 또는 AI 기반 개발자는 구현 속도는 높아졌지만 테스트 설계와 검증 경험이 부족한 경우가 많다.

결과적으로 서비스는 빠르게 만들어지지만, 출시 직전 핵심 기능을 검증하는 체계는 비어 있는 경우가 많다.

#### 2) 개발 주기 단축과 QA 부담 증가의 불균형

생성형 AI, 노코드 도구, 자동화 개발 환경의 확산으로 서비스 개발 속도는 과거보다 크게 빨라졌다. 반면 서비스 구조는 더 복잡해졌고, 로그인, 결제, 신청, 폼 제출과 같은 핵심 사용자 흐름은 오히려 더 많은 예외 상황을 고려해야 한다.

- 개발 시간은 줄었지만 QA 난이도는 낮아지지 않았다.
- 배포 주기가 짧아질수록 회귀 테스트 부담은 누적된다.
- 기능 수가 늘어날수록 테스트 유지보수 비용도 함께 증가한다.

즉, 현재 시장은 "개발은 빨라졌지만 QA는 여전히 느리고 비싸다"는 구조적 불균형을 안고 있다.

#### 3) 기존 QA 도구와 AI QA의 한계

기존 QA 도구는 자동화를 표방하지만, 실제 사용 단계에서는 여전히 높은 진입장벽이 존재한다.

- Playwright, Selenium, Cypress 등은 테스트 코드 작성과 유지보수가 필요하다.
- Low-code QA SaaS도 결국 사람이 시나리오를 정의해야 하는 경우가 많다.
- 최근 AI 기반 QA 도구 역시 테스트 코드 작성 보조 또는 자연어 기반 스크립트 생성 수준에 머무르는 경우가 많다.

이러한 구조에서는 개발 속도의 급격한 향상을 QA가 따라가지 못한다. 즉, 자동화 도구는 존재하지만 QA 비용을 본질적으로 낮추는 수준의 완전 자동화는 아직 충분히 제공되지 못하고 있다.

### 1-2. 문제 해결을 위한 창업 아이템의 필요성

#### 1) 개발 속도 증가에 대응하는 QA 자동화 필요

서비스 배포 속도가 빨라질수록 QA는 병목이 된다. 따라서 사람과 일정에 의존하던 기존 QA 방식에서 벗어나, 짧은 시간 안에 핵심 사용자 흐름을 자동으로 검증할 수 있는 솔루션이 필요하다.

#### 2) 전공자와 비전공자 모두를 위한 QA 접근성 개선 필요

현 시장의 QA 자동화 도구는 대체로 개발자 중심이다. 그러나 실제 현장에서는 PM, 기획자, 창업자도 배포 전 품질 확인에 참여해야 한다. 별도 학습 없이 URL 입력만으로 QA를 수행할 수 있는 직관적 구조가 필요하다.

#### 3) 도메인 입력만으로 문제를 도출하는 QA 특화 기술 필요

초기 조직은 테스트 시나리오를 세밀하게 설계할 여력이 부족하다. 따라서 사용자가 URL과 간단한 우선순위만 입력해도, 시스템이 핵심 퍼널을 인식하고 사용자 행동 기반으로 테스트를 실행한 뒤 문제를 구조적으로 리포트할 수 있어야 한다.

#### 4) QA를 선택이 아닌 필수 프로세스로 전환할 필요

초기 조직은 QA 필요성을 체감하면서도 비용과 시간이 부족해 QA를 생략하는 악순환에 빠진다. QA 수행 비용을 낮추고 실행 시간을 줄여야만 QA가 "있으면 좋은 절차"가 아니라 "배포 전 필수 절차"로 자리 잡을 수 있다.

## 2. 개발 방향성 및 해결 방안

### 2-1. 기존 문제점에 대한 해결 방안에 따른 개발 방향성

QAI는 범용 테스트 작성 도구가 아니라, `배포 전 핵심 퍼널의 장애를 자동 검증하고 배포 보류 여부를 판단하는 Agentic QA Release Gate`로 개발하고 있다.

이 방향성이 필요한 이유는 명확하다.

- 초기 고객은 "테스트를 예쁘게 만드는 도구"보다 "지금 배포해도 되는지 판단해주는 도구"를 더 절실히 원한다.
- 범용 QA 플랫폼부터 시작하면 경쟁 범위가 너무 넓어지고 초기 구현 난이도도 커진다.
- 반면 로그인, 결제, 신청, 폼 제출 같은 고위험 퍼널은 고객 pain이 명확하고 도입 가치가 즉시 설명된다.

즉, QAI의 개발 방향은 "모든 테스트를 대체하는 플랫폼"이 아니라 "배포 전 반드시 확인해야 하는 핵심 퍼널을 빠르게 검증하는 실용적 자동 QA"에 맞춰져 있다.

### 2-1-1. 차별성

QAI의 핵심 차별성은 `사람이 시나리오를 정의하는 구조`에서 `AI가 사용자 행동을 생성하고 실행하는 구조`로 전환하는 데 있다.

| 구분 | 기존 QA 도구 | QAI |
| --- | --- | --- |
| 테스트 정의 방식 | 사람이 시나리오 및 테스트 코드 작성 | AI가 퍼널 구조를 기반으로 실행 계획 생성 |
| 실행 방식 | Script/Rule 기반 고정 실행 | 실제 사용자 행동 기반 동적 실행 |
| 사용 대상 | 주로 개발자 및 QA 엔지니어 | 개발자, PM, 기획자, 창업자까지 사용 가능 |
| 초기 진입 방식 | 툴 학습, 설정, 유지보수 필요 | URL 및 계정 정보 입력만으로 시작 가능 |
| 결과물 | 실행 성공/실패 중심 | 재현 경로, 증거, 심각도, 배포 판단까지 제공 |
| 핵심 가치 | 테스트 자동화 | 배포 의사결정 자동화 |

### 2-1-2. 기술 기반의 문제 해결 방식

QAI는 Agentic AI를 무제한 탐색형으로 사용하는 것이 아니라, `제약된 에이전트 워크플로우`로 사용한다. 이를 통해 AI의 유연성과 기존 자동화의 재현성을 함께 확보한다.

현재 제품 구조는 다음 단계로 구성된다.

1. Discovery Agent: 진입 페이지의 구조와 CTA, 폼, 링크를 수집
2. Planner Agent: 선택된 퍼널에 맞는 실행 계획 생성
3. Browser Executor: 실제 브라우저에서 클릭, 입력, 이동 수행
4. Evidence Collector: 스크린샷, 콘솔, 네트워크 오류 등 증거 수집
5. Judge Agent: 수집된 evidence를 기반으로 기능 장애 여부 판정
6. Verifier: 중요 finding을 재검증해 false positive 감소
7. Reporter Agent: 최종 리포트와 배포 가능 여부 제시

이는 기존 테스트 자동화와 비교해 다음과 같은 기술적 정당성을 가진다.

- 단순 스크립트 재생이 아니라 퍼널 중심의 실행 계획을 자동 생성한다.
- 브라우저 액션은 deterministic하게 수행해 재현성과 안정성을 확보한다.
- AI는 계획, 판정, 리포트에 집중해 불안정성을 통제한다.
- 단순 성공/실패가 아니라 근거 기반 보고서까지 자동 생성한다.

### 2-1-4. 기술 개발 1차 MVP에 따른 User Flow

1차 MVP는 "URL 입력만으로 핵심 퍼널을 검증하고 배포 판단까지 제공"하는 흐름을 목표로 한다.

#### MVP User Flow

1. 사용자가 preview 또는 staging URL을 입력한다.
2. 사용자가 테스트 계정과 점검할 퍼널을 선택한다.
3. QAI가 진입 페이지를 분석하고 퍼널 실행 계획을 생성한다.
4. 브라우저에서 실제 사용자처럼 클릭, 입력, 이동을 수행한다.
5. 실행 과정에서 오류, 끊김, 콘솔 에러, 네트워크 실패를 수집한다.
6. QAI가 심각도와 재현 경로를 포함한 리포트를 생성한다.
7. 최종적으로 `배포 가능` 또는 `배포 보류` 판단을 제시한다.

#### MVP 경쟁력

- URL 입력만으로 시작 가능한 Zero Setup 구조
- 실제 사용자 행동 기반 탐색으로 정적 테스트의 한계 보완
- 증거 기반 리포트 자동 생성으로 QA 커뮤니케이션 비용 감소
- QA 전담 인력이 없는 팀도 바로 사용할 수 있는 접근성 확보

## 3. 사업화 추진 전략

### 3-1. 경쟁사 분석

#### 3-1-1. 경쟁사 현황 분석

| 구분 | Script 기반 자동화 도구 | Low-code / QA SaaS | Agent 기반 초기 시장 | QAI |
| --- | --- | --- | --- | --- |
| 대표 유형 | Playwright, Selenium, Cypress | mabl, testRigor | Momentic 등 | Agentic Release Gate QA |
| 기본 방식 | 개발자가 코드 작성 | GUI 기반 시나리오 구성 | 자연어 + 일부 자동화 | 퍼널 기반 자동 실행 + 배포 판단 |
| 장점 | 재현성 높음 | 진입장벽 일부 완화 | 최신 AI UX 제공 | 배포 직전 핵심 기능 검증에 특화 |
| 한계 | 작성/유지보수 비용 큼 | 시나리오 정의는 여전히 사람 중심 | 안정성, 재현성, 적용 범위 불명확 | 초기에는 퍼널 범위가 제한적 |

#### 3-1-2. 경쟁사 한계점 분석

1. 테스트 정의가 여전히 사람 중심이다.  
테스트 시나리오를 직접 설계하고 관리해야 하므로 자동화 효율이 제한된다.

2. 정적 테스트 구조에 머무른다.  
사전에 정의된 경로만 실행하는 경우가 많아 예외 상황 탐색이 어렵다.

3. QA 진입장벽이 여전히 높다.  
개발자와 QA 엔지니어 외 직군이 쓰기 어렵고 협업 비용이 크다.

#### 3-1-3. 자사 차별화 전략

1. Script-less 기반 완전 자동 QA  
테스트 코드와 시나리오 작성 없이 URL과 계정 정보만으로 실행 가능

2. 동적 탐색 기반 Agent QA  
사전 정의된 경로만 재생하지 않고 실제 사용자 행동 흐름을 따라가며 검증

3. 실제 사용자 행동 기반 테스트  
기능 단위가 아니라 로그인, 결제, 신청 등 실제 전환 퍼널 중심으로 테스트

4. 사용자 친화적 QA 환경  
비개발자도 사용할 수 있는 입력 구조와 결과 리포트 제공

5. 테스트 자동 생성 및 리포트 자동화  
실행 계획 생성부터 evidence 수집, finding 판정, 배포 판단까지 일관된 자동화 제공

### 3-2. 목표 시장 진입 전략

#### 3-2-1. 목표 시장 정의

QAI의 1차 목표 시장은 `QA 전담 인력이 없는 초기 조직`이다.

- QA 전담 인력이 없는 스타트업
- 개발자 1~5명 규모의 소규모 SaaS 팀
- PM 또는 기획자가 직접 QA를 수행하는 조직
- preview/staging 환경에서 빠른 배포를 반복하는 팀

#### 3-2-2. 초기 타깃 선정 이유

- QA 필요성은 높지만 인력과 시간이 부족하다.
- 기존 QA 도구를 도입하고 운영할 여력이 낮다.
- 배포 속도가 경쟁력인 조직이므로 release gate 가치가 크다.

#### 3-2-3. 시장 진입 전략

- 웹 기반 SaaS로 제공해 별도 설치 없이 즉시 사용 가능하게 설계
- URL 입력만으로 테스트를 시작할 수 있도록 진입장벽 최소화
- 초기에는 로그인, 결제, 신청 등 고위험 퍼널에 집중
- 베타 고객 확보 후 사례 중심으로 레퍼런스 확장

#### 3-2-4. 시장 규모 및 성장 가능성 (TAM / SAM / SOM)

QAI의 시장 규모는 `상위 시장 규모`와 `초기 타깃 고객군 기반 bottom-up 산정`을 함께 제시하는 것이 설득력이 높다.

##### TAM

- Statista는 `South Korea Application Development Software` 시장의 2025년 매출을 `US$2.87bn`으로 제시한다.
- 환율은 `1 USD = 1,350원`으로 가정하면, 이는 약 `3.87조원` 규모다.
- 이는 QAI가 속한 상위 소프트웨어/개발도구 시장의 국내 TAM으로 해석할 수 있다.

계산식:  
`US$2.87bn × 1,350원 = 약 3.87조원`

##### SAM

- 벤처기업협회 `2023 벤처기업정밀실태조사`는 벤처확인 법인기업을 `32,224개사`로 추정했다.
- 이 중 `소프트웨어개발/IT기반 서비스 13.6%`와 `정보통신/방송서비스 11.4%`를 합치면, 디지털 제품형 기업 비중은 `25.0%`다.
- 따라서 QA 자동화의 잠재 수요가 높은 기술 기반 벤처기업은 약 `8,056개사`로 추정할 수 있다.
- 이 중 실제 QAI의 초기 이상적 고객군(웹 서비스 운영, preview/staging 사용, 전담 QA 부재)에 해당하는 비중을 `35%`로 보수적으로 가정하면 `2,820개사`다.
- 연평균 고객당 매출(ARPA)을 `480만원`으로 가정하면, 초기 접근 가능 시장은 약 `135.4억원`이다.

계산식:  
`32,224 × 25.0% = 8,056개사`  
`8,056 × 35% = 2,820개사`  
`2,820 × 480만원 = 약 135.4억원`

##### SOM

- 초기 3년 내 현실적 목표는 위 SAM 중 `120개사`를 확보하는 것이다.
- 연평균 고객당 매출을 동일하게 `480만원`으로 두면, 3년 차 실현 가능 매출은 약 `5.76억원` 규모다.
- 이는 전체 상위 시장 기준으로는 매우 작은 점유율이지만, 초기 스타트업 SaaS의 현실적인 첫 점유 목표로는 충분히 방어 가능한 수치다.

계산식:  
`120개사 × 480만원 = 5.76억원`

##### 해석

- TAM은 충분히 크고 성장 중인 개발도구/소프트웨어 시장이다.
- SAM은 `QA 인력이 부족한 기술 기반 벤처기업`으로 좁혔을 때도 의미 있는 규모를 가진다.
- SOM은 초기 3년 기준으로 보수적으로 잡았으며, 실제로는 에이전시, 커머스, 예약 서비스 등으로 확장 시 추가 확대가 가능하다.

### 3-3. 비즈니스 모델

#### 3-3-1. 서비스 제공 구조

- 웹 기반 SaaS 제공
- 사용자는 URL, 계정, 퍼널 정보 입력 후 실행
- 결과는 실행 로그, evidence, finding, verdict 형태로 제공

#### 3-3-2. 수익 모델

1. 월 구독형 기본 요금제  
팀 단위 사용 권한, 실행 횟수, 리포트 저장 기능 제공

2. 사용량 기반 과금  
브라우저 실행 수, 테스트 시간, 고급 리포트 기능 등에 따라 추가 과금

3. 고급 기능 업셀링  
협업 연동, 팀 히스토리, 반복 장애 분석, 커스텀 퍼널 템플릿 등 유료화

#### 3-3-3. 수익 확장 전략

- 초기 스타트업 대상 저가 SaaS로 진입
- 검증된 사용 사례를 바탕으로 에이전시 및 중소기업으로 확장
- 이후 커머스, 예약, 핀테크 등 고위험 도메인 특화 QA 솔루션으로 확장

## 4. 심사위원 설득 포인트

### 4-1. 왜 이 방향의 개발이 타당한가

QAI는 "AI가 테스트를 대신 해준다"는 넓은 메시지보다, "배포 직전 핵심 퍼널이 실제로 동작하는지 자동으로 검증하고 배포 판단까지 제공한다"는 명확한 문제 해결 방향을 택하고 있다. 이는 초기 고객의 pain이 가장 크고, 기존 경쟁 도구가 충분히 해결하지 못한 영역이기 때문이다.

### 4-2. 왜 지금 가능한가

- 브라우저 자동화 기술이 성숙해 실제 사용자 행동 재현이 가능하다.
- AI는 계획 생성, 장애 판정, 리포트 작성 영역에서 생산성을 크게 높일 수 있다.
- 초기 시장은 범용 QA 플랫폼보다 배포 직전 smoke QA 수요가 더 분명하다.

### 4-3. 왜 이 팀이 할 수 있는가

대표자는 실제 개발 과정에서 QA 비용 부족과 검증 공백을 직접 경험했고, 이를 해결하기 위해 제품을 설계하고 구현 중이다. 즉, 문제를 외부에서 관찰한 것이 아니라 직접 겪은 pain에서 출발했기 때문에 고객 문제 정의와 제품 방향성이 밀접하게 연결되어 있다.

현재 초안에서 추가로 보강하면 설득력이 더 커지는 항목은 아래와 같다.

1. TAM / SAM / SOM 수치화  
전체 품질 엔지니어링 시장이 아니라, `초기 SaaS 팀 대상 웹 QA 자동화 시장`으로 좁혀 계산식 제시 필요

2. 고객 확보 전략 구체화  
예: 스타트업 커뮤니티, 개발자 네트워크, 베타 인터뷰, 무료 파일럿 전환 구조

3. 사업비 집행 계획 수치화  
개발비, 인프라, 브라우저 실행 비용, 마케팅 비용, 인건비로 구체화 필요

4. 실증 지표 확보  
MVP 테스트 횟수, 버그 탐지 사례, 예상 시간 절감 효과 등 숫자 확보 필요

5. 사업 추진 일정 표 고도화  
월 단위로 개발, 베타, 고객 검증, 유료 전환 목표를 수치로 넣어야 함

## 6. 현재 구현 반영 사항

2026-03-22 기준 저장소에는 아래 기능이 실제 구현되어 있다.

1. 제약된 Agentic QA 워크플로우  
Discovery, Planner, Browser Executor, Evidence Collector, Judge, Verifier, Reporter 흐름이 코드로 연결되어 있다.

2. 핵심 퍼널 중심 QA 실행  
login, checkout, form 퍼널에 대해 실제 브라우저 기반 실행과 evidence 수집이 가능하다.

3. 우선 점검 요청 입력 기능  
사용자가 URL, 계정, 환경, 퍼널과 함께 `우선 점검 요청 1줄`을 입력하면 Planner와 Reporter가 이를 반영한다.

4. mac 환경 실행 보강  
브라우저 실행기에서 macOS Chrome, Edge, Chromium 경로를 탐지하도록 확장해 mac 개발 환경에서도 바로 실행할 수 있도록 보완했다.

즉, 현재 프로젝트는 단순 아이디어 수준이 아니라, `배포 전 핵심 퍼널을 자동 검증하고 evidence와 verdict를 제공하는 MVP`가 구현된 상태라고 설명할 수 있다.
